# Many Live File Boards — Design

**Дата:** 2026-08-31 · **Статус:** APPROVED (owner: «ок» на дизайн 2026-08-31)
**Проблема:** живая файловая полоса ровно одна. `BOARD_PATH` в `vite.config.ts:30` — одна строка
из `SOVERN_BOARD`, `serveBoard()` вешает один маршрут `/board.canvas`, `ensureFileBoard()`
(`useWorkflowStore.ts:475`) по устройству заводит единственную вкладку `kind: 'file'`.
Смотреть два живых борда одновременно нельзя; переключение — правка переменной и рестарт дева.

Спрос пришёл из NAUTILUS: контур DataViz выводит из реестров лаборатории плиты и кладёт рядом
с каждой графовой борд `.canvas` (`docs/plates/observatory/*.canvas`). Сегодня их два, будет
больше, и открываются они по одному — вытесняя борд обратной связи mc_hub.

## Решение

**Живых бордов много; писать умеет ровно один.** Список приходит из окружения, вкладки
заводятся по списку, а способность к записи ВЫВОДИТСЯ из файловой системы, а не объявляется.

### 1. Источник списка — `SOVERN_BOARDS`

- Разделитель `;`. Двоеточие исключено намеренно: путь Windows содержит `C:`.
- Элемент списка — файл `*.canvas` **либо каталог**. Каталог разворачивается в свои `*.canvas`
  БЕЗ рекурсии: рекурсивный обход втянул бы `node_modules` и чужие артефакты.
- Порядок детерминирован: элементы — как перечислены, внутри каталога — по имени файла.
- `SOVERN_BOARD` (единственное число) остаётся и означает список из одного элемента.
- Заданы обе переменные → выигрывает `SOVERN_BOARDS`, и это **печатается в консоль**. Молчаливый
  выбор между двумя источниками правды — то, из-за чего потом полдня ищут «почему не тот борд».
- Обе пусты → дефолт прежний: `C:/telo/Efforts/Ongoing/mc_hub/feedback/board.canvas`. Обратная
  совместимость полная: у кого стоял `SOVERN_BOARD`, у того ничего не меняется.

### 2. Сервер (`vite.config.ts`)

- `GET /api/boards` → `[{ id, name, path, writable, mtime, error? }]`.
- `GET /board/:id.canvas` → содержимое одного борда.
- `GET /board.canvas` остаётся и отдаёт ПЕРВЫЙ борд списка — внешние потребители и старые
  вкладки не ломаются.
- **`id` — стабильный хеш пути, не индекс.** Индекс сдвинется при добавлении борда в середину
  списка, и содержимое вкладок молча поменяется местами.
- `name` — из `metadata['desops:title']` борда, если есть (борды NAUTILUS его несут), иначе имя
  файла без расширения. `board.canvas (live)` как имя больше не годится: оно описывало
  единственность.
- **Битый или пропавший файл не роняет список.** Такая запись приходит с `error` (строка с
  причиной), остальные борды живы. Правило 9: «не смог прочитать» обязано выглядеть иначе,
  чем «пусто». У записи с `error` нет `name` из содержимого — подставляется имя файла.
- Чтобы отдать `name`, сервер разбирает файл. Разбор кэшируется по паре `(path, mtime)`: иначе
  «клиент не тянет файлы целиком» превратилось бы в «их целиком тянет сервер на каждый тик».
- `writable` — результат ПРОБЫ: рядом с бордом лежит `scripts/fb.mjs`. Никакого конфига;
  способность выводится из файловой системы, как и сегодняшний `FB_CLI`.

### 3. Клиент

- `BoardMeta` получает `sourceId?: string` — ключ живого борда. `kind: 'file'` сохраняется.
- `ensureFileBoard()` → `syncFileBoards(list)`: заводит недостающие вкладки, убирает вкладки
  исчезнувших бордов, ключ — `sourceId`. Содержимое между бордами не течёт.
- Поллинг перестаёт тянуть файлы целиком: один запрос `/api/boards`, перечитывается только то,
  у чего сменился `mtime`, и только АКТИВНАЯ вкладка. Сегодня поллится весь файл каждые 3 с; с
  N бордами это N полных файлов на каждый тик.
- Вкладка с `error` показывает причину, а не пустой холст.

### 4. Запись — ровно одна полоса

- `/api/feedback/status` принимает `boardId` и берёт `fb.mjs` СВОЕГО борда.
- Борд без `writable` → **400 с внятной причиной**, а не тихий успех. Сегодня перетаскивание
  карточки на плите потоков ушло бы в `fb.mjs` из mc_hub с идентификатором, которого там нет.
- Канбан на не-writable вкладке не предлагает перетаскивание.
- Ручные правки на живых вкладках как не сохранялись, так и не сохраняются
  (`useAutosave.ts:21` пропускает `kind: 'file'`) — теперь это названо, а не подразумевается.

### 5. MCP-сервер

`resolveBoardPath()` = writable-борд: `SOVERN_BOARD`, иначе первый writable из списка. Артефакты
по-прежнему едут в одно место, контракт инструментов не меняется.

### 6. Инварианты

- Защита от StrictMode в `useBoardSync` сохраняется дословно: двойной прогон эффекта однажды
  залил содержимое живого борда в пользовательскую доску, и следующий переход по вкладке это
  сохранил. Переписывание на N бордов — ровно тот заход, где её теряют.
- Undo/redo и автосейв ведут себя как для любого борда: живые вкладки не персистятся.
- Один и тот же файл, названный в списке дважды, даёт ОДНУ вкладку (id по пути).

### 7. Тесты

- Разбор `SOVERN_BOARDS`: файлы, каталоги, смесь, пустое, обе переменные заданы, дубль пути.
- `id` стабилен при вставке борда в середину списка (мутационно: сделать id индексом → красное).
- Пропавший и битый файл → запись с `error`, соседи живы.
- `syncFileBoards`: добавление и удаление борда переставляют вкладки; содержимое не течёт.
- Запись: 400 на не-writable; write-back попадает в `fb.mjs` своего борда.
- StrictMode-защита: отдельный тест, что содержимое живого борда не садится на пользовательскую
  доску при двойном прогоне эффекта.

## Вне скоупа

Кнопка импорта `.canvas` в UI; редактирование живых бордов с записью обратно в файл; рекурсивный
обход каталогов; наблюдение за файлами через watcher вместо поллинга; шаринг и multi-window.
